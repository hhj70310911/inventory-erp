# ERP 第一版使用與部署

## 已完成
- 本機環境已與原官網分離；獨立 AUTH_SECRET、ERP_DATABASE_TARGET 與管理員憑證。
- 已將初始 migration 套用到獨立 Railway ERP 開發庫，並建立指定管理員。原官網資料庫未修改。
- 入口 /erp：商品 SKU、多倉庫、供應商、客戶、多明細採購入庫、銷售單、部分出貨、FIFO 批次成本、分次收款、毛利及欠款、員工權限和稽核紀錄。

## 正式部署前
1. 建立獨立正式庫，勿把 Preview 指向正式庫。
2. Vercel 設 DATABASE_URL、ERP_DATABASE_TARGET（host:port/database）、ERP_ENVIRONMENT=production、獨立 AUTH_SECRET、正式 NEXTAUTH_URL。
3. 以審查過的 migration 部署：npm run db:migrate:deploy。不要使用 db:push。
4. 管理員初始化在可信任環境執行 npm run db:seed；不在每次建置重複 seed。
5. 設定備份及驗證還原，完成正式驗收後才導入客戶真實資料。
尚未 Git push 或 Vercel 部署。

## Vercel 首次部署
1. 匯入 GitHub hhj70310911/inventory-erp，正式分支 main，Next.js，Root Directory ./，Node.js 24.x。建置指令由 vercel.json 指定 npm run build:vercel。
2. Railway 另外建立專用正式 PostgreSQL；目前本機使用的是開發庫，保持隔離。
3. Vercel Production 設定 DATABASE_URL（正式庫 Public URL 的實際值）、ERP_DATABASE_TARGET（正式庫 host:port/database）、ERP_ENVIRONMENT=production、全新 AUTH_SECRET。Preview 改用開發／測試庫及 ERP_ENVIRONMENT=test，不複製正式庫變數。
4. 第一次可先不設定 NEXTAUTH_URL，Auth.js 使用 Vercel 的請求網址；若手動設定，使用該環境 HTTPS 網址，不可填 localhost，Preview 不要沿用正式網址。
5. 建置流程先驗證環境，再 generate、next build，最後 migrate deploy；migration 失敗會阻擋這次部署。資料庫更新不可依靠網站 rollback 還原，往後 migration 需保持與上一版程式相容。
6. 正式库首次 migration 完成後，在可信任的本機以正式庫環境執行 db:seed 建立管理員；不在每次部署自動 seed，也不將 ADMIN_PASSWORD 放进 Git。
7. 部署後驗證登入、SKU／倉庫、入庫／出貨／收款及權限，再開始正式使用。

## 帳號管理
- 導覽列固定 09「帳號管理」：所有啟用的 ERP 使用者可核對目前密碼後修改自己的密碼。
- 僅 role=ADMIN 可重設其他啟用員工的密碼，須再次驗證管理員目前密碼。主管與一般員工不能呼叫重設 API，也不能重設其他 ADMIN。
- 建立員工、初始化管理員、修改與重設密碼統一至少 8 碼；bcrypt UTF-8 上限 72 bytes，超過會拒絕而非截斷。新密碼需再次確認。
- 密碼修改與稽核紀錄在同一交易；紀錄不含新舊密碼、雜湊或密碼指紋。
- 登入 token 綁定目前密碼版本；改密碼、重設或停用帳號後，舊登入不能繼續存取 ERP。此版本首次部署時既有登入須重新登入，原密碼不變。
- scripts/test-account-integration.ts 使用獨立測試 schema 驗證權限與密碼，再啟動 3101 隔離網站跑 scripts/test-account-browser.cjs；不修改正式庫帳號。

## 批次剩餘成本調整（2026-09-23）

- 「批次帳務」展開批次後，管理員／主管可輸入新單位成本及原因；同一批所有倉庫的剩餘庫存立即套用，數量不變。已無庫存或已沖銷的批次不能調整。
- 原始進貨成本保留於採購明細，入庫紀錄及進貨總成本不隨調價變更；目前庫存成本另行顯示。
- 確認出貨時保存批次成本版本、成本與售價快照；已出貨訂單及批次報表一律加總出貨快照，不以目前批次成本回算。
- 每次調整保存舊／新成本、當時剩餘數量、各倉庫數量、操作者、原因及系統時間。價值調整 =（新成本－舊成本）× 當時剩餘數量，與已出貨毛利分開顯示。
- 成本調整沿用原幣別及入庫匯率，不接受回溯生效日期；建立但未出貨的訂單會於實際出貨時採當時成本。
- 出貨沖銷仍保留原出貨快照；回庫商品採該批目前成本，重新出貨時建立新快照。有成本調整歷史的入庫單不可沖銷，以保留完整追溯鏈。
- 重複提交依 requestKey 防重，舊成本版本提交會被拒絕。調價與出貨均在 Serializable 交易中完成，衝突重試後重新讀取成本與餘量。
- 新遷移僅新增成本版本欄位（既有資料預設版本 0）及調整歷史表，沒有改寫既有成本或庫存。部署仍由 Vercel 執行 migrate deploy。
- 驗證：`node --import tsx scripts/test-batch-cost-integration.ts`，UI 驗證：先 build，再 `node --import tsx scripts/test-batch-cost-ui.ts`。僅使用 development/test 的隨機獨立 schema，結束後移除。

## 商品管理（已驗收並核准部署）
- 管理員及主管在商品目錄可編輯名稱、系列、單位、參考售價，SKU 編碼不變。單位編輯只更正文字，不進行數量換算。
- 刪除只允許沒有任何批次、採購明細、銷售明細的商品；含已沖銷歷史者不可刪除。AuditEvent 保存刪除前商品資料。
- 停用必須所有倉庫零庫存且 POSTED 訂單沒有待出數量。新進貨／銷售選單及庫存彙總排除停用品，但歷史報表保留。
- 已停用清單可重新啟用。沖銷出貨回庫前要求商品為啟用，避免停用品出現新庫存及待出貨量。
- updatedAt 驗證避免覆蓋其他人的編輯；操作以 Serializable 交易、防重 requestKey 及後端權限保護。
- 測試：先 build，再 node --import tsx scripts/test-product-integration.ts，使用隔離 schema 驗證並清理。
- 本次不需資料庫遷移；商品管理已經測試版驗收，使用者核准合併 main 並部署正式版。
